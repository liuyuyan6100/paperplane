# 分阶段实施与安装验收

每次只交付一个可以学习、操作和验证的单元。实现和自动回归完成后提供候选安装包；使用者安装验证，记录问题、修复并复验，通过后才推进下一阶段。持续集成成功不会自动推进阶段，也不会自动发布稳定版。

## 阶段安排

| 阶段 | 交付范围 | 使用者验证重点 | 进入下一阶段条件 |
| --- | --- | --- | --- |
| M0 框架基线 | 独立公开分支、架构决定、功能清单、回归基线、Wiki 索引 | 了解框架和每轮验收方式；本阶段没有安装包 | 分支和基线记录完成 |
| M1 文章编辑 | React/FastAPI 最小链路，文章列表、打开、编辑、预览、保存；旧功能通过兼容入口保留 | 新建合成文章、保存重开、未保存离开提醒、编辑期间后台刷新、多窗口冲突 | 自动测试、独立安装验证及用户确认通过 |
| M2 侧边 AI | 挂接现有模型与编辑助手业务，发送、讨论、改稿建议、对照、采用和撤销 | 未保存正文进入上下文；只讨论不改稿；选区处理；迟到建议与人工修改保护 | 合成回归、明确配置后的真实模型验证及用户确认通过 |
| M3 任务状态 | 任务查询契约、执行协议、轮询、失败分类、中断与人工恢复 | 页面切换后仍能查看原任务；关闭重开后状态正确；未知送稿不可直接重试 | 故障注入、备份恢复、防重复及用户确认通过 |
| M4 功能与数据兼容 | 逐项归并较新本地功能，完成数据访问与迁移接管、旧入口等价性 | 选定备份副本上的完整创作链、媒体、画像、平台稿与历史 | 功能清单全部有结论，升级/回退演练通过，用户确认 |
| M5 稳定交付 | 整理稳定版安装升级与正式数据迁移，收敛兼容区 | 正式升级后原数据和常用功能核对 | 单独完成稳定版发布与安装验收，不由前面阶段自动触发 |

M2 不是额外创造另一套写作模型，M3 不是重做所有平台。每阶段沿用既定业务语义。发现需要改变产品行为时记录差异；不得借架构整理静默改变提纲确认、正文采用或公众号送稿流程。

## 第一轮的范围

M1 先让新框架完成“打开一篇文章 → 编辑 → 保存 → 重开”的完整闭环，并验证多窗口冲突和后台刷新。新 UI 中没有迁入的功能必须保留明确的旧工作台入口；不能显示同名无效按钮，也不能提前宣称侧边 AI 已迁移。

第一份安装包须独立安装，显示“架构验证版”和阶段编号，显示数据目录。初始只使用合成示例或用户自行建立的测试稿；真实备份导入须另获授权。2026-10-18 用户已明确授权 M2 自动复用本机原纸飞机配置，按 M2 实施记录只读导入并保留验证版已有值，不要求逐项重填。旧工作台入口连接验证版自己的库，不转到正式运行端。

用户完成 M1 后，将实际体验、失败项和确认结果写回 [验收单](milestones/01-editor-acceptance.md)。如果失败则留在 M1 修复，不能用后续新功能代替修复。

## 文档节奏

每阶段维护：实现范围、架构变化、操作步骤、自动测试结果、候选包版本与 SHA256、安装核验、用户反馈、已知限制和下一阶段入口。公共文档只存脱敏结论；原始日志和个人反馈中的私密内容保留在本地证据目录。

Wiki 在仓库 `docs/wiki/` 维护索引，正文链接到权威文件；本机共享知识库仅链接归档入口。GitHub 独立 Wiki 未初始化，本轮不把它当作另一份已同步的文档库。
